## Загальна логіка

Бекенд розбитий на три проєкти в одному рішенні, не на кілька сервісів.

- `Project.Application` — сутності, контракти запитів/відповідей, інтерфейси операцій.
- `Project.Infrastructure` — робота з базою, паролі, файли, конкретні реалізації тих інтерфейсів.
- `Project.Api` — маршрути HTTP, підключення автентифікації, читання конфігурації.

Контролер не рахує ціну ночі і не пише SQL. Правило живе в сервісі. Нова функція: контракт у Application → реалізація в Infrastructure → маршрут у Api → сторінка в `Frontend/src/pages`.

Точка збірки бекенду — `Program.cs`: підключення бази (LocalDB або Postgres, якщо в рядку підключення є `Host=` і немає `localdb`), Identity, JWT, за бажанням Google, CORS, статичні файли з `wwwroot/uploads`, контролери. При старті: для LocalDB накладаються міграції, для Postgres схема створюється з поточної моделі. Потім `DataSeeder` додає навчальні акаунти й оголошення, якщо їх ще немає. Помилка наповнення логується, процес не падає.

## Модель даних і навіщо кожне поле

Контекст: `AppDbContext`, плюс стандартні таблиці Identity.

### Користувач (`AppUser`)

Розширення стандартного користувача Identity: відображуване ім’я, аватар, прапор `IsHost`, верифікація телефону (поле є, сценарію підтвердження немає), блок «про себе» для сторінки профілю (школа, професія, мови, місто, декада народження, інтереси, пісня, факт, тварини, короткий текст).

`IsHost` не роль у токені. Стає `true` при першому успішному створенні оголошення. З профілю його не знімають.

Пароль: довжина від 6, без обов’язкових класів символів. Email унікальний. Після реєстрації `EmailConfirmed = true` одразу — листа немає.

### Оголошення (`Listing`)

Ідентифікатор Guid, господар (`HostId`, видалення користувача з оголошеннями заборонене), тексти, адреса, широта/довгота, ціна за ніч, збір за прибирання, місткість, кімнати/ліжка/ванни, правила, політика скасування, `IsPublished`, час створення.

Категорія збережена двічі:

1. Поле `Category` — одне значення (як було спочатку).
2. Таблиця `ListingCategoryLinks` — складений ключ «оголошення + категорія», кілька значень.

Пошук: збіг із полем **або** з будь-яким рядком зв’язки. Форма господаря пише повний список у зв’язки і копіює першу обрану категорію в поле `Category`, щоб старі місця, які читають одне значення, не зламались.

Номери категорій (ті самі, що в JSON на клієнті):

0 краєвиди, 1 невеликі квартири, 2 великі квартири, 3 хостели, 4 luxe, 5 центр, 6 сільська місцевість, 7 від дизайнера.

Підписи українською — масив `CATEGORIES` у `Frontend/src/api/client.ts`. Змінювати треба синхронно з переліком у `ListingCategory.cs`.

### Фото (`ListingPhoto`)

URL і `SortOrder`. URL або зовнішній (наповнення з інтернету), або `/uploads/listings/{ім’я}`. Ім’я файлу при завантаженні — новий Guid, розширення з оригіналу. Дозволені `.jpg` `.jpeg` `.png` `.webp`. Не більше 12 фото на оголошення. Запит на завантаження обмежений приблизно 5 МБ.

`mediaUrl` на клієнті: якщо рядок уже з `http`/`https` — підставляється як є; інакше додається `VITE_API_ORIGIN` (локально в `.env` фронту це `http://localhost:5176`), щоб `<img>` знайшов файл на API. Відносний `fetch('/api/...')` іде через проксі Vite на той самий порт.

Видалення фото з диска лише якщо URL починається з `/uploads/listings/`. Зовнішні навчальні картинки не чіпаються.

### Зручності - !!!СИРІСТЬ!!!

`Amenity` + зв’язка `ListingAmenity`. Наповнювач створює Wi-Fi, кухню, паркінг, кондиціонер і вішає частину на оголошення. Форма господаря зручності не редагує. Картка оголошення показує те, що є в базі.

### Бронювання (`Booking`)

Дати без часу (`DateOnly`). Гість, оголошення, кількість людей, план оплати (повна / частинами — зберігається, на суму не впливає), сума, статус, повідомлення господареві.

Статуси: 0 очікує оплату, 1 підтверджено, 2 скасовано, 3 завершено. У інтерфейсі створюється 0 і після заглушки оплати стає 1. Скасування і завершення не реалізовані.

Сума: `(дата виїзду − дата заїзду в днях) × ціна за ніч + прибирання`. Заїзд 10-го, виїзд 12-го → 2 ночі.

Підтверджене бронювання блокує інтервал для пошуку і для нової оплати. Неоплачене — ні.

Видалення користувача-гостя при наявності броней обмежене (Restrict), як і для господаря оголошення.

### Оплата (`Payment`)

Рядок після заглушки: сума = сума броні, метод 0–3 (карта, PayPal, Google, Apple), статус завжди «заглушка успішна». Банківського виклику немає.

Сторінка «Мої способи оплати» пише дані лише в `localStorage` браузера. Бекенд про збережені картки не знає.

### Відгуки та обране !!!НЕ РЕАЛІЗОВАНО ЩЕ!!!

Таблиці `Review` і `Favorite` є. Середній рейтинг і кількість відгуків рахуються в картці та деталях. Створити відгук або додати в обране з клієнта не можна.

Грошові поля в моделі з точністю два знаки після коми; рейтинг — три знаки, два після коми.

Міграції: початкова схема і таблиця зв’язок категорій. Фабрика `AppDbContextFactory` — для команд оновлення схеми на LocalDB.

## Автентифікація на практиці

### Пошта і пароль

`POST /api/auth/register`, `POST /api/auth/login`. Тіла відповідають `RegisterRequest` / `LoginRequest`.

Реєстрація: порожній або різний пароль → помилка; зайнятий email → помилка; інакше `UserManager.CreateAsync` і токен.

Вхід: немає користувача або невірний пароль → 401 з текстом про пошту/пароль.

Відповідь: `accessToken`, `displayName`, `email`, `isHost`.

Токен: HMAC-SHA256, ключ з секції `Jwt` (локально рядок у `appsettings.json`). У токені: ідентифікатор користувача (`sub` і `NameIdentifier` — той самий id, його читають контролери), email, відображуване ім’я. Термін — `ExpiresMinutes` або 120 хвилин. Видавець і аудиторія — рядок `EverywhereHome`.

Клієнт: `setSession` у `session.ts` тримає токен у змінній і в `localStorage` як `eh_token`, повідомляє підписників і шле подію `eh-auth`. Шапка підписується в `useLayoutEffect`, щоб після логіну одразу показати меню акаунта (без цього React Strict Mode встигав відписатися, і шапка лишалась «гостьовою» до оновлення сторінки).

`api()` підставляє `Authorization: Bearer …`, для JSON ставить `Content-Type`. Відповідь не 2xx — кидає `Error` з `message` тіла. Код 204 (видалення оголошення) тіла не чекає.

Вийти: `setSession(null)`, перехід на головну.

Захищені контролери: атрибут авторизації, id з `NameIdentifier`. Немає токена → 401.

### Google, кнопки Apple і Facebook - !!!ТІЛЬКИ Google налаштовано!!!Потребує доменного імені!!!

`GET /api/auth/providers` — чи задані ключі Google / Facebook / Apple. Клієнт малює всі три кнопки; якщо прапор хибний, поруч підказка, що ключів немає.

Клік Google: повний перехід браузера на `/api/auth/external/google`

`LoginOrRegisterExternalAsync`: знайшли прив’язку провайдера — токен цього користувача; немає прив’язки, є email — `AddLoginAsync` до існуючого; нікого немає — користувач без пароля + прив’язка.

Повернення на клієнт: `{Frontend:Url}/auth/callback?token=...`. Параметр саме в query. Решітка відкидається при HTTP-редіректі — через це вхід колись зависав на «Завершуємо вхід».

`AuthCallbackPage` читає `token` або `error`, зберігає сесію, замінює адресу на `/`.

""""""Локальний Google: User Secrets, дозволений redirect `http://localhost:5176/api/auth/signin-google`. Apple і Facebook в коді передбачені тими ж дверима `external/{provider}`, ключів і обробників схем немає — завжди текст, що ще не готово.""" -

Параметр `iss` у відповіді Google зрізається перед обробкою, щоб бібліотека не падала. Збій зовнішнього входу перекидає на callback з текстом помилки, а не порожню сторінку 500.

## Пошук і картка оголошення

`GET /api/listings` — список. Параметри query: `q` (фрагмент назви), `city` (фрагмент міста), `guests`, `minPrice`, `maxPrice`, `categories` (можна кілька разів), `checkIn`, `checkOut`, `page`, `pageSize`.

Ланцюжок фільтрів (усі необов’язкові, між собою логіка «і»):

- лише `IsPublished`;
- назва: `Contains` після Trim;
- місто: так само;
- гості: `MaxGuests >=` заданого, якщо число > 0;
- ціна від/до: якщо значення > 0;
- категорії: головне поле або будь-яка зв’язка з переданого списку;
- обидві дати і виїзд пізніше заїзду: немає підтвердженого бронювання з перетином  
  `існуючийЗаїзд < новийВиїзд && існуючийВиїзд > новийЗаїзд`.

`pageSize` приймається лише 25, 50, 100; інше стає 25. Сторінка менше 1 стає 1. Сортування за назвою. У картці: середнє оцінок або 0, перше фото за `SortOrder`.

`GET /api/listings/{id}` — повна картка, тільки опубліковане. Фото всіма URL, зручності назвами, господар ім’ям і аватаром. Немає або знято з публікації → 404.

Головна (`HomePage.tsx`): компактне поле назви, кнопка панелі фільтрів, вибір розміру сторінки. Параметри збираються в рядок запиту; категорії додаються повторюваним ключем. Перше завантаження — сторінка 1.

Сторінка оголошення: карусель, збільшення фото, блок бронювання (дати, гості, план, повідомлення). Без токена бронювання не пройде.

## Бронювання і заглушка оплати

`POST /api/bookings` (потрібен вхід). Перевірки по порядку в `BookingService.CreateAsync`: виїзд пізніше заїзду; хоча б один гість; оголошення існує і опубліковане; не своє житло; гостей не більше за `MaxGuests`; немає підтвердженого перетину дат; тоді запис зі статусом «очікує оплату».

Два неоплачені інтервали на ті самі дати допустимі. Конфлікт вирішується на оплаті.

`GET /api/bookings` — лише свої, новіші вище.  
`GET /api/bookings/{id}` — лише своя, інакше 404.

`POST /api/bookings/{id}/pay-stub` з полем методу. Якщо вже підтверджено — повернути як є (повторне натискання безпечне). Якщо статус не «очікує оплату» — відмова. Знову перевірка перетину з **іншими** підтвердженими. Успіх: статус підтверджено + рядок `Payment`.

Клієнт: `/bookings`, `/bookings/:id/pay`. Підписи статусів — масив `BOOKING_STATUS` у `client.ts` (індекс = число з бази).

## Кабінет господаря !!!В подальшому буде реалізовано окрему привілегію - домоволодільця (господаря)!!!

Усі шляхи `/api/host/listings`, потрібен вхід. Чужий id → «оголошення не знайдено».

| Дія               | Метод і шлях                    | Поведінка                                                            |
| ----------------- | ------------------------------- | -------------------------------------------------------------------- |
| Список            | GET `/`                         | свої, новіші вище                                                    |
| Читання для форми | GET `/{id}`                     | поля + список категорій + фото                                       |
| Створення         | POST `/`                        | валідація, за потреби `IsHost=true`                                  |
| Оновлення         | PUT `/{id}`                     | ті самі правила, зв’язки категорій перезаписуються                   |
| Видалення         | DELETE `/{id}`                  | є підтверджена бронь → лише `IsPublished=false`; інакше рядок з бази |
| Додати фото       | POST `/{id}/photos`             | multipart, поле `file`                                               |
| Прибрати фото     | DELETE `/{id}/photos/{photoId}` | файл + рядок                                                         |

Валідація введення: непусті назва й місто; ціна > 0; гості ≥ 1; хоча б одна категорія. Рядки обрізаються. Ванни менше 1 стають 1.

Екрани: `/host/listings`, `/host/listings/new`, `/host/listings/:id`. Вибір категорій — той самий компонент, що на головній (`CategoryPicker`).

## Наповнення бази при старті

Якщо немає господаря/гостя з поштами вище — створюються. Зручності — якщо немає за назвою. Каталог оголошень: набір по українських містах, фото з зовнішніх URL. Повтор за назвою не додається.

Локально після міграцій каталог з’являється сам. Якщо список порожній — або порожня інша база, або `Seed failed` у логу API.

## Де змінювати поведінку

Правило видачі списку житла — `ListingService.cs`, маршрут `ListingsController.cs`, екран `HomePage.tsx`.  
Правило броні та суми — `BookingService.cs`.  
Оголошення господаря і ліміт фото — `HostListingService.cs`, файли — `LocalFileStorage.cs`.  
Видача токена — `AuthService.cs`. Google-цикл — `AuthController.cs` і блок Google в `Program.cs`.  
Сесія в браузері — `session.ts`. Усі виклики — `client.ts`.  
Список сторінок — `App.tsx`. Поля профілю в базі — `AppUser.cs` + `ProfileService.cs`.

Практичний спосіб розібратись: пройти один сценарій (пошук → картка → реєстрація → бронь → оплата-заглушка → створити оголошення) і на кожному кроці відкрити сторінку, маршрут `/api/...` і сервіс, який ставить `SaveChanges` або рахує фільтр.


## Frontend language support
The frontend now includes a persistent Ukrainian/English language switcher in the top-right corner. The selected language is stored in localStorage under `eh_language` and the default is Ukrainian.

## Extended application features
The existing frontend and backend remain intact and were extended with additional screens that use the existing API contracts:

- Favorites: view and remove saved listings; listing details can add/remove a favorite.
- Messaging: guest support, listing conversations, host conversations, and admin support replies.
- Host application: submit identity/document information and view application status.
- Admin panel: review host applications, reports, users, and support conversations.
- The existing Ukrainian/English language switcher covers the added screens as well.

The backend already contains the required services, controllers, persistence models, and migrations for these features, so the extension reuses those APIs instead of replacing existing backend code.
